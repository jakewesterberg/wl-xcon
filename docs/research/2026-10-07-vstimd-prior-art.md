## 2. Architecture
- Process model: one daemon (systemd service, usually root for CAP_SYS_NICE, docs/operations/deployment.md:~168) with two threads sharing Arc<RwLock<SceneState>>: render thread (vsync-locked) and ZMQ thread (docs/developer/architecture.md "Threads"). Rule: render thread never blocks or heap-allocates on event emission.
- Protocol: ZMQ REQ/REP over TCP :5555, protobuf (docs/developer/protocol.md:4,55; proto/vstimd/v1/*.proto), plus a PUB event stream (docs/concepts/event-stream.md), HTTP/WebSocket UI on :8080, mDNS discovery. Clients: Python (maintained), JS web UI, C#/Bonsai usable, MATLAB planned (docs/concepts/how-vstimd-works.md).
- Not per-frame lockstep. The design is "trigger-driven": scenes and small on-device animations are set up ahead, driven by Virtual Trigger Lines (shared-memory bit bank polled at the start of each frame, outputs committed after present, daemon/ vtl crate; docs/concepts/vtl-and-animations.md). The command API is explicitly "not the tool" for within-frame reaction (how-vstimd-works.md). Deferred mode stages commands and flips them atomically; reply gives `flip_frame` (docs/concepts/deferred-mode.md). So the frame-by-frame lockstep wl-xcon wants from a Python trial loop is not what it is built for; each command is a ZMQ round-trip (doc estimate ~100-400 us, UNMEASURED in-repo, see below).
- Per-frame loop (docs/developer/architecture.md "Render loop"): acquire image, deferred flip, poll VTL, advance animations, CPU tessellate dirty stimuli (lyon), upload buffers, render pass (stimuli + egui overlay), vkQueuePresentKHR, commit VTL outputs, wait for vblank.
- Timing mechanism: present mode always VK_PRESENT_MODE_FIFO (daemon/src/render/vk/vk_context.rs:307,473); MAILBOX only for benchmarks. Direct display via VK_KHR_display (no compositor). Frame pacing waits on a vblank-source chain (docs/developer/frame-timing.md, rendering.md): (1) DRM_IOCTL_WAIT_VBLANK, (2) VK_EXT_display_control FIRST_PIXEL_OUT (~330 us after vblank at 120 Hz; used on Jetson), (3) VK_KHR_present_wait, (4) GPU fence (labeled inaccurate). It deliberately does not block on vkAcquireNextImage so inputs are not a frame stale. SCHED_FIFO for the render thread via `[scheduling] render_rt_prio`, on by default (deployment.md). No busy-wait spin found in docs. No VK_EXT_present_timing / VK_GOOGLE_display_timing use (grep of daemon/src: only present_wait/display_control).
- Late frame: not recovered or skipped-ahead. A drop is detected after the fact: interval > 1.5x expected (dev/FRAME_TIMING.md "Layer 1"; daemon/src/timing.rs on_present), counted, sparkline in overlay F7, and published as `frame.dropped` events (proto events.proto:131-143, FrameDropped with count and total_since_start) and via FrameStats / ResetFrameStats queries (system.proto:95-125: presented, dropped, mean/std/min/max interval). Animations advance by real frame time so a drop is visible (animations.proto:93).
- Timing reporting: frame number is the unit of truth, with monotonic_us per event (event-stream.md:62-67). Frame index ties to `flip_frame` and VTL markers.
- Measurement: the claim of "guaranteed frame timing" is not backed by committed numbers. The only latency table (docs/developer/frame-timing.md:12-20) is an estimate (ZMQ 100-400 us, vsync 0-16.7 ms, render 0.5-2 ms, panel 1-10 ms, total ~2-30 ms at 60 Hz), no method given. A photodiode patch and tutorial exist (docs/tutorials/photodiode-flicker.md; "the gap between them is the number you quote in a methods section"), but no photodiode results, oscilloscope traces or jitter figures were found in docs/ or dev/. Only measured numbers: DRM_IOCTL_WAIT_VBLANK returns <2 us on an evdi device and a Pi 5/DisplayLink frame budget (docs/developer/evdi-direct-presentation-plan.md:112,268), irrelevant to us. dev/FRAME_TIMING.md still describes wgpu `SurfaceTexture::present()` (stale; code is ash), and Layer 2+ (hardware-in-the-loop) is "planned". Treat "guaranteed" as marketing, UNVERIFIED.

## 3. Stimulus model
- Types: Rect, Circle, Ellipse (fill+outline), Grating (masked drifting sine/square/saw/triangle), Text (cosmic-text glyph atlas), Dots (random dot kinematograms, GPU), 3-D Cube/Sphere/Plane, Gaussian-splat scenes (vsplat). Polygon schema exists, not accepted; bitmap/image/texture pipeline "planned" (rendering.md "Implementation status"; the latest merge name mentions an SD image, state UNVERIFIED). No movie playback found.
- Description: created via protobuf commands (handles, per-stimulus pos px from screen centre Y-up, rotation, opacity, enabled, draw order = creation order, conditions) or declarative versioned JSON scene config saved on device (docs/concepts/saving-loading.md). Shaders WGSL in daemon/shaders/ (solid, grating, dots, text, mesh3d, splat, veil, egui).
- Color: Color = f32 RGBA "linear" per daemon/src/color.rs, but swapchain is B8G8R8A8_UNORM with SRGB_NONLINEAR color space (vk_context.rs:461,786; screenshot.rs:176). So 8-bit output. No 10-bit/A2B10G10R10, no HDR, no gamma table or measured LUT, no calibration anywhere (grep for gamma/LUT/10-bit/HDR in daemon/ and docs: no hits except unrelated). A gap against your needs.
- Stereo / multiple viewports: none (no stereo or viewport hits). Single framebuffer, single scene.
- Photodiode: one always-on-capable corner patch, a scene setting (`scene.photodiode.enabled`, `flicker`), drawn by the renderer; flicker inverts every frame, and an animation action TOGGLE_PHOTODIODE toggles it on animation start/final/cancel (animations.proto:191-235; tutorials/photodiode-flicker.md:58-72). So both of your patches are expressible in concept (frame clock = flicker, task patch = toggle per change), but only one patch with no position/size command in v0.1.
- Scale: CPU tessellation per dirty stimulus each frame (lyon), shared RwLock between command thread and render; scaling to thousands of elements at 4K/240 Hz is UNVERIFIED (no benchmark in repo; a criterion dev-dependency exists).

## 4. What wl-xcon could learn or reuse
Legal: AGPL-3.0 daemon. Linking code from it into an Apache-2.0 work is not possible without making the combined work AGPL; any copied/adapted source triggers the same, and AGPL section 13 adds network-use source obligations. ADR-0004 says a copyleft dependency reopens the license decision, so do not copy or link daemon code. Only the LGPL-3.0 Python client could be used as a separate dependency, but it speaks vstimd's protocol, so is useful only if vstimd itself is adopted as an out-of-process server (running vstimd as a separate unmodified process and talking over ZMQ is generally not a derivative work; a license review is still needed, and I am not a lawyer). Ideas, protocol facts and documented techniques are not copyrightable, so learn from the docs and re-implement cleanly (ideally one person reads, another writes, or just cite the docs).
Techniques worth taking (all re-implement from the Vulkan spec, verify yourself):
1. VK_KHR_display on NVIDIA with DRM master released to Vulkan; avoid VK_EXT_acquire_drm_display (their bare-metal.md reason is Jetson-specific, so does not apply to a desktop RTX; verify).
2. Vblank clock hierarchy and the observation that blocking on acquire under FIFO leaves inputs one frame stale; instead wait on a post-flip vblank signal, then compute the frame. Also the VK_EXT_display_control details: instance extension VK_EXT_display_surface_counter, device ext VK_EXT_display_control, VkSwapchainCounterCreateInfoEXT with VBLANK bit or vkRegisterDisplayEventEXT fails with ERROR_UNKNOWN (rendering.md:75-86).
3. FIFO only; MAILBOX makes the visible frame unknowable.
4. Dropped-frame accounting as an event with a cumulative counter plus per-frame number so consumers can detect their own loss (events.proto, event-stream.md:120-129); frame index as the unit, microseconds secondary.
5. Deferred mode: stage then commit one atomic flip and return the `flip_frame` (maps directly to wl-xcon's "which frame did this change land on").
6. Photodiode patch as renderer-owned scene state, not a stimulus handle, so a stray command cannot remove it.
7. Build-time shader compile (naga) so shader errors are build errors; SCHED_FIFO with explicit failure surfaced in diagnostics; null renderer for CI (the sim-first rule).
Fit as an off-the-shelf engine: poor. Command-per-frame lockstep, 10-bit output, measured LUT, mirror stereo viewports and thousands of elements are all missing, and the license is AGPL.

## 5. Risks and gaps
- Maturity: alpha, 7 months old, wire protocol unstable, authors say not for data collection; no published photodiode validation, so the timing guarantee is a design claim.
- Bus factor: one human maintainer plus AI agent commits; institutional backing is a single lab. Release cadence active (alpha4 on 2026-09-25).
- Focus: Jetson Orin Nano/Pi 5 embedded boards at 60/120 Hz-class; only a GTX 1650 desktop tested. Nothing on RTX 50-series, 240 Hz, 4K, QD-OLED, or driver version quirks (they document an nvidia-modeset VRR bug on JetPack 6.x, 0x22).
- Design mismatch: REQ/REP over a network, trigger-driven; round-trip per command, no per-frame lockstep guarantee.
- Missing vs wl-xcon needs: 10-bit, LUT/gamma, calibration, stereo/dual viewports, textured images and movies, large-N element throughput evidence, two independent patches.
- Licensing: AGPL for daemon (blocks reuse in Apache-2.0 work), LGPL client.
- Unverified: whether the latest merge adds image stimuli; actual NVIDIA desktop vblank source selected on RTX 50; real jitter numbers.
