## 1. DECIDED

### 1.1 The split: declarative trial, between-trial Python (ADR-0006; PI, 2026-08-31, Accepted)
- ADR-0006 Decision 1: "Within a trial, task logic is declarative data. States, guarded transitions, entry/exit actions, outcome codes. `taskd` executes it; the task never owns the frame loop."
- Decision 2: "Between trials, task logic is ordinary Python. Condition selection, block progression, staircases, adaptive updates. Outside the frame budget, errors are observable and recoverable, and the freedom costs nothing."
- Decision 3: representation is "Python declarations (dataclass/pydantic) in plain-text, diffable files — not a bespoke text DSL, not YAML/JSON, not a GUI builder, not database-stored tasks."
- Rejected alternative, same ADR: "Pure state machine with no imperative layer at all. Rejected: between-trial concerns (staircases, block logic, condition balancing) express badly as graphs and gain nothing from being one, since they are outside the frame budget."
- Decision 6 / S1 §8: no Python inside a trial; novelty is a typed, named `Custom` component in framework source, flagged for human review.
- S1 §4 (the only statement of the between-trial surface): "Ordinary Python, called at trial boundaries, outside the frame budget: condition selection and block progression (the scheduler, S8); staircases and adaptive parameter updates; re-queue policy for aborted trials; any computation that produces the *next* trial's parameters. It may read the running statistics the console plots and the scheduler share. It writes parameters only through the validated path (parent §7.2), and by default may not write them at all — the console and the external control API are the enabled writers."
- S1 §5.3 / §7 (bake-off finding, author unnamed, ADR-0006 deciders PI): "Task B turned out not to be a discriminating case at all ... the argument that adaptive tasks need imperative trials confuses between-trial adaptation with within-trial control." Illustrative signature (S1 §5.3, "illustrative, not shipped", line 8): `def next_trial(session, history): ... return Params(contrast=staircase.value, target_position=session.block.sample_position())`, with `session.state["staircase"]` and `session.block`.
- Review artifact (ADR-0006 Consequences; S1 §6; S9 "The gate"): a task is approved from "a rendered state diagram, a timeline, a condition/code table, and a simulation report." S1 §9 and the spec map say the acceptance test is "a generated task can be reviewed from a diagram and 5,000 simulated trials without reading source."

### 1.2 Vocabulary (PI, 2026-10-01; SL §2, "decided")
"The PI, 2026-10-01: block means a set of conditions ('1, but it is important that blocks are temporal instances')." Table: Session = one animal's visit cage to cage; Task = a task program named by file; Run = one start-to-stop of one task; **Block type** = "A named set of conditions, e.g. Bt1. In code, a `scheduler.Block`."; **Block** = "One stretch of consecutive trials under one block type, inside one run. Block types recur, and each occurrence is a new block."; Condition = "One set of parameter values a trial runs under. A block type holds one or more."; Trial = one instance.
- "A run ending mid-block closes that block ... A block lies inside one run." (SL §2)
- The PI's own sentence (SL §1): "a session that can be multiple tasks, each task can be run multiple times, and tasks can have a block structure where a set of trials has a specific set of conditions. trials are the individual instances." Block recurrence: "Bt1 to Bt2 to Bt1 to Bt2 is Block 1 to Block 2 to Block 3 to Block 4".
- wl-works' glossary row "block = one run of one task" is superseded; "What it called a block is a run." (SL §2, §8; wl-works told 2026-10-01).

### 1.3 Targets, counts, length rules
- PI, 2026-09-19 (`docs/next-session.md` ~line 714; S8 §4 and §8 item 7): "There is no session length max. Sessions will be comprised of multiple tasks with perhaps multiple blocks of the same tasks. Each task, depending on its config, will have a target number of trials (likely per condition within the task). But the max trials idea makes no sense to me." Consequence: `max_trials` deleted; "per-condition targets are `scheduler`'s (`Counts`, `owed()`, `upcoming()`)" (S8 §8 item 7).
- S8 §1: length rules "fixed N, or criterion-based ('80% correct over the last 20 completed trials'). Criterion transitions consume the same running statistics the console plots use, computed once."
- S8 §2: "Counters distinguish attempted / completed / correct, per condition. Collapsing them makes a balanced design unverifiable." "The console shows achieved against target, because the question at a rig is never 'how many have I run' but 'how many more do I need.'"
- What counts toward a condition's target is **declared per block**, PI 2026-08-31 (`scheduler.py:24-32`, `Counting`): "'Run until ten correct' and 'show the array a hundred times regardless of accuracy' are both ordinary requirements ... A scheduler that picked one would silently impose an experimental design on every task in the lab."
- Criterion judged over a set separate from the counted set (`Block.criterion_over`, `scheduler.py:141-145`): "conflating the two makes a criterion track engagement rather than what the animal can do."

### 1.4 Ordering and randomization
- S8 §2: "Randomisation is seeded and the seed is recorded, so a session's condition order is reconstructable." Order is declared per block (`scheduler.py:87-122`, comment "Declared per block (PI, 2026-08-31)"): `Shuffled`, `WithReplacement(weights)`, `Constrained(max_run, weights)`.
- Block order: a plan is an ordered `list[Block]`; "multiple blocks of the same tasks" may reuse the same `Block` object (`taskd.py:2171-2179` comment, quoting the PI's description of 2026-09-19).

### 1.5 Aborted trials: requeue (PI, 2026-08-31; S8 §2, §8 item 3 "Answered")
"Default (PI, 2026-08-31): a fixation break is re-queued at the end of the block; a wrong choice is not. ... End of block rather than immediately, so the animal cannot make an easy condition repeat by breaking on the hard one. Overridable per block." Code default `scheduler.REQUEUED` is wider than this (section 5 item 1).

### 1.6 Adaptivity and parameter writes
- Parameters: each task declares name, type, unit, range, live-editable or not (S8 §3.1; built as `task.Param`, `task.py:121`). Starting values are the task's own, on `Param.start` (P4d2b §6.2, §6.7 plan decision 1; PI 2026-09-29/30 via the b3a-2 plan). Remembering an animal's last values is XC-018, open.
- Application: "Staged, then applied atomically in the ITI. Never mid-trial." "If regenerating derived stimuli overruns the ITI, the ITI extends. Frames are never dropped." "Values and structure are both live; logic is not — a task reload happens at a trial boundary and is logged as a discontinuity" (S8 §3.2).
- "Every trial records a complete resolved parameter snapshot, not a pointer to 'the config.'" (S8 §3.3). `docs/CHECKPOINT.md` ~line 3195: "Every trial records its block and condition ... Two conditions can resolve to identical values — a catch trial and a signal trial ... an analysis grouping by parameters would silently merge them."
- "One validated write path, whatever the origin — console, external control API, or the task itself. Origin and actor are recorded. In-task writes are off by default." Arbitration of concurrent writers: proposed only (S8 §3.3; S8 §8 item 1 open).
- Precedence (S8 §3.4): "deployment → rig → subject → task → session → live edits, all under the bounded config's ceiling. The resolved set is snapshotted per trial; the layers are recorded too."
- Staircase doctrine: `tasks/adaptive_detection.py:1-11` docstring and S1 §5.3. Only the *call* is missing (section 2).
- Reward/stimulation: tasks name bounded-config entries, never magnitudes (S1 §2.3; S8 §4).

### 1.7 Who chooses blocks now that the day's plan is retired
- Old rule (S8 §1, S3 §7, P4d2b §4.0): "Blocks are planned in wl.works before the session" and an unplanned block lowered the timing tier. P4d2b §4.0 (line ~181): PI chose "plan first, unplanned allowed".
- **Retired 2026-10-01**: P4d2b §4.0 dated note: "the PI retired this ruling ('Nothing; retire the ruling'), as recorded by wl-works, `6a57b1cc` (its spec `2026-10-01-montage-plan-design.md` §1 and §6). wl.works sends the rig no day's plan; block plans and conditions come from the task programs (wl-xtasks) or are chosen at the rig (backlog XC-207); and wl-preproc withdrew the quarantine the timing-tier cost rested on. Every run is just a run." (The wl-works spec itself is outside this repo and was not read: UNVERIFIED beyond these quotations.)
- S3 §7 "Overtaken 2026-10-01" note: "Whether a session opens with calibration is decided at the rig."
- Backlog XC-207 (2026-10-01, waits on wl-xtasks): "a task declares its block types, their conditions and their order, or the rig picks one at run start". The mechanism is **not designed**. Two sources named, neither specified: (a) the task program declares them, (b) the rig picks at run start.
- `scheduler.py:7-13` docstring repeats it: "This schedules *within* the blocks a run is given and never invents one."
- Block order within a run is not specified anywhere beyond "an ordered list."

### 1.8 Session-levels numbering (PI, 2026-10-01; SL §3, approved with one change)
Ten position numbers on every `trials.jsonl` line: `trial_number`, `trial_in_task`, `trial_in_run`, `trial_in_block`, `block_in_session`, `block_in_task`, `block_in_run`, `run_in_session`, `run_in_task`, `task_in_session`. `block` keeps the block *type* name, `condition` the condition name. PI chose to include run levels ("Yes, all of them") and number tasks by first appearance ("Distinct task order"). The strip's block line shows `block_in_session` (PI reviewing SL, §6). A run ending mid-block closes it; a faulted block "is still a block".
- Trial numbering (XC155 §2.2): counts from 1 across the whole session, held in `Session` beside `_sequence`; a faulted trial keeps its number; the number is strobed (`TRIAL_NUMBER`) and written as `trial_number`. PI approved 2026-09-30 ("Looks right, write it up").
- `CONDITION` escape: "He also chose to leave `CONDITION` for later ('Wait until conditions exist')." (XC155 header, §2.3). "nothing yet says who numbers conditions."

### 1.9 Other session-structure decisions touching the layer
- Interludes (S8 §1): "sub-tasks the session enters and leaves without ending. Calibration is the motivating case; an interlude creates no block." Calibration: "Calibration uses both mechanisms (PI, 2026-08-31)": a planned block (retired by 2026-10-01 note) plus in-task `CALIBRATION_START/END` epochs (S3 §7).
- One run = one task = one `Trial`. `cli._load_trial` (`wl_xcon/cli.py:37-52`) requires exactly one `Trial` instance among a module's attributes: "defines {n} trials; expected exactly 1".
- A change of task type is a new run (`scheduler.py:13`); live edits of weights/geometry are free (S8 §1).
- Resume (XC-026, built 2026-10-02; S8 §6): "block and trial indices carry forward from the record" (numbers only; scheduler state is not restored, see 2.3).
- Free-viewing / multiple responses per trial (S1a §8, settled 2026-08-31): "Trials emit scored events; the terminal outcome summarises", with `Score(window, outcome)`. "This needs its own design pass" for intermediary outcomes.

## 2. BUILT

### 2.1 Scheduler (`wl_xcon/scheduler.py`, 298 lines): complete, used in production only for a degenerate plan
- `Condition(name, values: dict, target: int)` (125-129); `Block(name, conditions, criterion, counts_toward, criterion_over, requeue_on, order)` (132-152); `Counting` presets `RESPONDED`, `CORRECT_ONLY`, `PRESENTED`, `EVERY_TRIAL` (24-59); `REQUEUED` (75-84); `Shuffled`/`WithReplacement`/`Constrained` (87-122); `Counts(attempted, completed, correct)` (155); `Scheduler.next_trial/record/owed/upcoming/finished/done/advance` (162-298). `owed` = target minus completed (217-224). `advance` resets counters, criterion window and queue (245-265). `requeued` list is the session log of reruns (169), reset never.
- The seed: `Scheduler(blocks=self._plan(run), seed=run.seed)` (`taskd.py:2024`); `run.seed` is written in `runs.jsonl` start row (`taskd.py:2038`).
- **Production use**: `taskd.Session.run` drives it every trial: `next_trial` (`taskd.py:2199`), `record` (2264), `finished/done/advance` (2154-2196). But every production run gets the flat plan from `_plan` (below). A real `list[Block]` reaches `Session.run` only through `RunSpec.blocks` / `SessionSpec.blocks`; grep finds no caller outside `taskd.py` and tests that sets `blocks=` (the 3 block tests, `tests/test_taskd.py:967-1042`: `_two_blocks`, "shaping/test").
- `taskd._plan` (`taskd.py:1798-1815`): returns `run.blocks` if given, else one `Block("session", [Condition("session", {}, target=run.trials)], counts_toward=frozenset(Outcome))`. Comment: "Every trial pays, including aborts. A flat 'run N trials' means N trials." So in a flat run the requeue rule can never fire (`record`: requeue only `if outcome not in counts_toward`), the condition is named "session", `condition.values == {}`.
- Per trial: `values = {**self.spec.values, **condition.values}` (`taskd.py:2200`); `world = make_world(trial, values, index)` (2201); `run_trial(..., values=values, ...)`. The same `Trial` object every trial; only `values` can differ. Because the layering puts `condition.values` last, **a condition's value silently beats a live console edit to the same parameter** (inference from that line; S8 §3.4 lists live edits last). Console parameter panel reads `spec.values` (`taskd.py:1086`), not the resolved per-trial set.
- Telemetry: publishes `block` name and `owed = {c: scheduler.owed(c) for c in scheduler.upcoming()}` (`link.py:690`, 730; docstring 535), i.e. "still needed" only for conditions currently queued; `Counts` (attempted/completed/correct) are published nowhere (grep: `.counts(` has no consumer outside scheduler tests). `Scheduler.requeued` has no consumer outside tests.
- Tests: `tests/test_scheduler.py`, block tests in `tests/test_taskd.py`. Mutation harness covers `scheduler.record` (backlog XC-140: times out in CI).

Block type name for the strip comes from `self._scheduler.block.name` (`taskd.py:1030`).

### 2.3 What is only in tests / not built
- `calibration.conditions(geometry, window_deg, hold_s, timeout_s, repeats)` (`calibration.py:696-735`) turns the 13-point `constellation` (383-429) into scheduler `Condition`s named `target_00..12` with values `target_x/target_y/cal_window/cal_hold/fix_timeout`. Called only in `tests/test_calibration.py:502,524`.
- `gaze.Calibrating` (`gaze.py:207-300`): a driver plugging into `Session` through `world` and `observe`; "a session runs blocks, and what a particular block is *for* is not the session's business." Constructed only in `tests/test_gaze.py:635,743`. `Session.world` and `Session.observe` hooks (`taskd.py:316, 319`) are never set by production code (`grep 'observe=\|world='` finds nothing in `wl_xcon/`). SCI §3: "`calibration.conditions` and `gaze.Calibrating` are used only by tests."
- `adaptive_detection.Staircase` and `next_params(staircase, eccentricity, last)` (`tasks/adaptive_detection.py:128-172`): called only from `tests/test_reference_tasks.py:110-131`. Nothing in `wl_xcon/` loads or calls it (SCI §2: "its between-trial hooks (`make_world`, `observe`) are the framework's"). The module loader ignores everything but the single `Trial`. `contrast` and `eccentricity` are declared Params but "read by **no** stimulus, window or guard" (SCI §2; `check.parameters_used` returns neither). `next_params` is a free function with a bespoke signature; no protocol exists. Its rule moves the staircase only on CORRECT vs WRONG_TARGET.
- No task declares blocks, conditions, orders, targets or a staircase hook in a form the framework reads. `tasks/fixation_detection.py:3` docstring says "a target appears at one of six positions" but `target_position` is one starting value (10.0) and nothing varies it (SCI §3). `visual_search.py:99` "Randomised between trials so the animal cannot learn positions" is likewise a comment; `array_phase`, `target_index`, `set_size` have no start and no varier.
- Interludes (S8 §1): `grep -i interlude wl_xcon tasks` returns nothing.
- Tokens (`Token`, `SetPersistent`, cross-trial persistent state): specified in S1 §2.3, "implemented nowhere" (S1 §10 item 3; S8 §5.3 finding, 2026-09-20; XC-009). A task has no cross-trial state place at all; a staircase object lives in whatever calls it.
- Appearances (categorical `Param`, e.g. `target_looks`) cannot be set by any run: `preflight.values` refuses non-`choices` values, the page/`--set` carry numbers and words (SCI §4; `preflight.py:154-156`; `Param.__post_init__` refuses a non-numeric `start`). So a condition that swaps appearance (the "circles among squares" design in each task's comment) cannot be given as a condition value today either: `condition.values` bypass `preflight.values` entirely (preflight checks `spec.values` + starts only: `preflight.py:114-186`) and `Session.set`; per-condition values are validated by nothing (inference from code; no test read).
- Simulation: `simulate.simulate` (`simulate.py:326-371`) runs N identical trials with fixed `values`, no scheduler, no blocks; `Tally`/`Census` (261-290) count outcomes and scored responses by `(window, classification)`; the census is not per condition, per block or per parameter. `Subject` hazards are keyed by guard *type* (`simulate.py:43,182-219`), so the simulated animal's behavior cannot depend on contrast, set size or any condition value (inference). `prepare()` is per trial because "an array's per-item windows are not known until `n` is bound and `n` can be a condition's value" (`simulate.py:293-303`): the one place the simulator expects per-trial values, but the real default world `_agent` (`taskd.py:1820-1835`) is the only caller that passes them.
- Review artifact (`wl_xcon/review.py`): renders trial structure, event codes, windows, parameters (ranges), stimuli, display timeline, "needs human review" (lines 142-241). **No blocks, conditions, orders, targets or between-trial code section.** ADR-0006's "condition/code table" is today a code table only.
- Check (`wl_xcon/check.py`): reasons over declared parameter *ranges* (e.g. `target-outside-array`, S1a §12), not over a block plan's concrete values; it has no notion of Block or Condition (grep: no `Block`/`Condition` in `check.py`, `review.py`, `preflight.py`, `run.py`).

## 3. WHAT THE RECORDING AND wl-preproc EXPECT

(`wl-preproc/` is a link into `.superpowers/wl-preproc-main`; files read: `wl_preproc/contracts/events.py`, `contracts/nwb_description.py`, `nwb/conditions.py`, `events/rigtrials.py`, `schema/events.py`, `docs/pending-wl-xcon-amendments.md`. - A run that faults sends neither `BLOCK_END` nor `RUN_END`; wl-preproc closes the block at the next run's start / last event (`schema/events.py:194, 327-334`; `nwb/intervals.py:65-75` `closed` = 1 / 0 / -1).
- **XC-197 (open, waits on XC-207)**: wl-preproc ask 2, quoted from its `docs/pending-wl-xcon-amendments.md`: "Emit `CONDITION` inside every trial, a number for the condition it ran under, and record that number in `trials.jsonl` beside the condition's name, so the name and the stream's number can be tied without a table kept anywhere else." Backlog: "decide then who numbers conditions". No numbering rule exists anywhere. Not decided: whether the number is per task, per block type, per session, or per file; whether it is stable across runs.

With the record: condition identified **by name**, with settings constant across its trials and a summary of those that varied (`min/max` for numbers, distinct values up to 20 otherwise). - `TARGET_POSITION` escape exists (role, x, y in DVA); S2 §3 and XC-029 (open: disparity field) concern it; nothing in wl-xcon emits it. Whether a task's per-trial target position goes in the stream is undecided (S2 §4 lists it among "what must survive"): UNVERIFIED whether wl-xcon has a backlog line other than XC-029.
- wl-preproc withdrew the unplanned-block quarantine: reports "an unlinked block, reported and harmless" (S3 §7 note, citing wl-preproc `docs/pending-wl-works-amendments.md` `b0f8b52`).

## 5. CONTRADICTIONS AND STALE STATEMENTS

1. **Requeue: spec vs code.** S8 §2 and §8 item 3: "a fixation break is re-queued at the end of the block ... End of block rather than immediately, so the animal cannot make an easy condition repeat by breaking on the hard one." Code (`scheduler.py:294-298`): `self._queue.append(condition)` onto the current draw queue. Run 2026-10-07 (small script, not the suite): with `Shuffled` a requeued condition goes to the end of the *current pass* (queue `['a']` becomes `['a','b']`), not the block; with `WithReplacement` the queue holds one draw, so the requeued condition is the very next trial (queue `[]` becomes `['a']`, next drawn `a`). Also `REQUEUED` (`scheduler.py:75-84`) is `FIXATION_BREAK, NO_FIXATION, TARGET_BREAK, BLINK_BREAK, TRACKER_LOST, FAULT`, wider than the PI's one-line ruling; the comment says rig faults were added 2026-09-01 (no PI date given for the widening). And in the only production plan (`_plan`, `counts_toward=frozenset(Outcome)`) the rule is inert.
2. **S8 §1 stale and unmarked** (XC-208): "Blocks are planned in wl.works before the session (S3 §7)" and its definition "Blocks — one run of one task, mirroring `wl-preproc`'s `core.Block`" are both superseded (plan retired 2026-10-01; block means "stretch of trials under one block type" per SL §2, and "one run of one task" is now a run). S8 §8 item 5 ("Who plans blocks when wl.works is unreachable") stale. `docs/CHECKPOINT.md` and `scheduler.py:7-13` are current.
3. **Dangling reference**: S1a §3 ("`AwardToken()` / `TakeToken()` | token economies (S1 §5.6)") and S8 §5.3 ("S1 §5.6") cite a section that S1 does not have (S1 §5 ends at 5.3; tokens appear in S1 §2.3 and §10 item 3).
4. **S1 vs S1a naming**: S1 §2.3 lists `Emit`, `Token(+1 / -1)`, `PlaySound`, `SetPersistent`; S1a §3/§6 renames `Mark`, `AwardToken/TakeToken`, `Play`; code has `Mark` (task.py:1011) and neither Token action. S1 §5.1 imports `from wl_exptasks.codes import EV` (package since renamed wl-xtasks; XC-142).
5. **S1 §5.3's `next_trial(session, history) -> Params`** (with `session.state`, `session.block.sample_position()`) vs shipped `next_params(staircase, eccentricity, last) -> dict` returning a fixed set of timing values plus `contrast`/`eccentricity` (`adaptive_detection.py:154-172`): different shape, different arguments, returned dict names a param (`eccentricity`) the task's windows never read and omits `target_position` and `fix_window`. No interface bridges them.
6. **S1 §4 "may not write parameters at all by default; only the validated path"** vs `next_params` returning a whole values dict, which presumably would be applied by the framework; no such application path exists, so which writer/actor ("the task itself", S8 §3.3) records it is unspecified. `actor.py` has only `Box` and `Member`; no actor kind for an in-task writer.
7. **Condition value layering vs S8 §3.4**: spec says live edits are the last layer; code makes `condition.values` the last layer (`taskd.py:2200`). No condition has values in production so it is latent.
8. **S8 §2 "console shows achieved against target"** vs built: telemetry carries only `owed` (remaining, queued conditions, `link.py:730`), no `Counts`; the strip's tallies are outcome counts by session/task/run/block (`levels.py`), not per condition.
9. **XC-197 vs wl-preproc's note**: wl-preproc `docs/pending-wl-xcon-amendments.md` and XC155 §2.3's original text say "XC-150, the day's plan"; backlog and SL say XC-207 (SL header notes the change). Stale pointer on wl-preproc's side (not editable here).
10. **Docstring vs reference tasks**: `fixation_detection.py:3` "a target appears at one of six positions" and `visual_search.py:99` "Randomised between trials" describe variation nothing performs (SCI §3); `adaptive_detection.py:1` "mini-blocks of held eccentricity" has no block declaration anywhere; DM §6 table calls `contrast` 1.0 "the staircase's ceiling: it starts easy and comes down" (false: SCI §2; DM §14 item 2 already lists it for rewrite).
11. **`calibration.py` comment (`calibration.py:696-715`) and `tasks/calibration.py:10-14`** state "the scheduler walks them one trial each" and "an animal that refuses one simply leaves that condition short": true of `Calibrating` in tests; with `Session` in production nothing builds that block. `tasks/calibration.py:21-24` also says the stereoscope calibration task is XC-005, "not yet written".
12. **Docs say `taskd` "draws blocks from a scheduler"** (`taskd.py:3-5`), true, but `pitfalls.md:234` records that `scheduler.py` once went unwired; today it is wired but starved of a plan: the CLAUDE.md "safety component ships with its consumer" shape, here for experiment structure rather than welfare.
13. **S3 §7 note says "Block plans and conditions come from the task programs (wl-xtasks) or are chosen at the rig"** while `docs/CHECKPOINT.md`/XC-207 say the same; but where wl-xtasks is "an empty scaffold today" (P4d2b §6) and the reference tasks in this repo's `tasks/` have no place to say it, the "task program" route has no format yet.
14. **Census/`simulate` vs scheduler**: S1a §8 says "The census counts responses as well as outcomes"; true (`Tally.responses`). But the census is per task, not per condition, and `Position.lone` fixes it to one run of one block, so a design's balance cannot be verified by it (S8 §2: "Collapsing them makes a balanced design unverifiable").

## 6. DECISIONS A DESIGN MUST TAKE (INFERENCE, mine; not a repository statement)

Marked **PI** where the choice is science-facing or animal-facing (and per CLAUDE.md "Ask, do not file" goes to Jake as a question), **ENG** where it is an engineering call, **BOTH** where the shape is engineering but a default is a PI call.

A. Where a run's plan lives and who writes it (XC-207).
 1. Does a task module declare its blocks, conditions, order and targets (a second object beside the single `Trial`, since `cli._load_trial` accepts exactly one `Trial`)? Or does a separate "program" file sit above the `Trial`? Or does the rig pick at run start (and from what UI)? **ENG** for format; **PI** for whether the rig operator may choose conditions/targets live, and who may (sign-in actors exist).
 2. Does a plan allow several different `Trial`s in one run? Today "one run = one task = one Trial" (SL §2) and a task change is a new run (`scheduler.py:13`). Interludes (S8 §1) are unbuilt. **ENG**, with a **PI** check that "interlude creates no block" still holds with the 2026-10-01 vocabulary.
 3. Are block types given stable names that recur? SL §2 needs that ("Bt1"); `BLOCK_START` carries only `block_in_session` and task code, so type identity lives only in `trials.jsonl`. Whether block type needs a stream code is wl-preproc/wl-xtasks. **ENG** (with a wl-preproc ask if wanted).

B. Condition semantics.
 4. A condition is `values: dict` over declared params. Needs: validation of condition values against `Param` ranges and choices at load (today unchecked), and what happens to appearance-valued params, which `Param.start`/`preflight`/`Session.set` refuse. **ENG**.
 5. Precedence of live edits against condition values (code: condition wins; spec S8 §3.4: live edits last). **BOTH**: engineering rule, but whether a console edit may override a design's condition is science-facing.
 6. How per-trial randomized values (target position, array phase, target index, set size) are expressed: as enumerated conditions (the scheduler's model, each a named condition with a target count), or as sampled-per-trial parameters with a distribution (what `visual_search.py:99` and `fixation_detection.py:3` imply). The census, the recording's condition name and `CONDITION` number all key on the former. **PI** (it is the experimental design) with **ENG** for the mechanism.
 7. Numbering of conditions for `CONDITION` (XC-197): scope (task / block type / session / file), stability across runs and across edited task versions, and whether it may be 0-based. The 16-bit escape payload is a uint32. **ENG** (wl-preproc agreement needed; PI asked when due per the rule).

C. Targets, counting, order.
 8. Default `counts_toward`/`criterion_over`/`requeue_on` for a task's blocks. Today's only production default is "every trial counts", which makes a flat run N trials and makes requeue inert. The PI ruled on requeue (S8 §2) but code diverges (section 5 item 1). **PI** (animal-facing: how many trials/how much work; science-facing: which aborts owe a datum).
 9. Reconcile the requeue implementation with the ruling ("end of block, not immediately") or change the ruling; define "end of block" for `WithReplacement`/`Constrained`. **PI** to confirm intent; **ENG** to fix.
 10. Which `Order` is the default and whether orders compose across blocks (e.g. interleaved block types, block-type recurrence rules like Bt1,Bt2,Bt1,Bt2, block-level randomization with its own seed). Block-order rule is wholly unspecified. **BOTH**.
 11. What ends a run: all blocks done, a criterion, or an operator stop; whether a criterion block that never reaches criterion may run forever (there is no per-block cap; there is no session-length maximum by PI ruling, only the 8 h out-of-cage limit). **PI** (welfare/animal-facing; the PI ruled out `max_trials`).
 12. Whether achieved vs target is shown per condition (Counts published; S8 §2) and whether Telemetry's schema grows (it is at 12). **ENG**.

D. Between-trial code.
 13. The interface: when it is called (after `scheduler.record`, before `next_trial`?), what it receives (S1 §5.3's `session, history`; running statistics; last outcome; scheduler state), what it returns (a full values dict, a delta, a condition choice), and whether it can pick the next condition or only adjust values. **ENG** (shape); today there is none (XC-242).
 14. Where its state lives (staircase object): per run? per block? carried across runs of a task, or from an earlier session (XC-018)? In every per-trial snapshot (S8 §5.3: "otherwise a token balance is exactly the 'pointer to the config' failure")? Restored on resume (resume restores numbers only)? **BOTH**: state persistence is engineering, but carrying an animal's threshold across days is science-facing.
 15. How its writes are authorized and recorded: actor, `PARAM_CHANGE`/`parameter_changes.jsonl` rows per adaptive step or per-trial `params` only; bounded-config names must be unreachable (S1 §2.3). Interaction with the validated path and arbitration (S8 §3.3, open). **ENG**; welfare-adjacent: any path touching reward amount stays refused by `Session.set`/bounds, so a between-trial function must not be given a route to `bounds`. Flag for **human welfare review** if the design touches `Session.set` (it is on the welfare list).
 16. Whether between-trial code runs in the trial-boundary pass on the loop thread (budget: it sits inside the ITI, `taskd.py` boundary; "If regenerating derived stimuli overruns the ITI, the ITI extends"), with a timeout and a fault policy (an exception must never take the session down with an animal in the chair; `Session.run`'s fault handler ends the run). **ENG**.
 17. The staircase rule itself: which outcomes move it (misses never move it today), catch/target-absent trials, floor/ceiling, step, convergence point, whether `NO_RESPONSE` counts as a miss. SCI §2 and CHECKPOINT step 3 say these are the PI's decisions "to ask then, in the UI". **PI**.
 18. Token economy (XC-009): whether the first design includes cross-trial persistent state or leaves it out; the conversion rule; recording. **PI** for conversion (welfare-adjacent, goes through `welfare.deliver`); **ENG** for state declaration.

E. Verification and review.
 19. Extend `review.py` and `check.py` with a plan section (blocks, conditions, targets, order, requeue policy, the between-trial function) and checks (every condition value within declared range; every condition names declared params; every condition reachable; targets non-zero; criterion windows attainable; plan terminates). ADR-0006's acceptance test requires it ("A task nobody could review from those alone has failed the design"). **ENG**; "Prove a test can fail": `tools/mutate.py --all` on new modules (CLAUDE.md).
 20. Extend the simulator: scheduler-driven census per condition and per block; a `Subject` whose behavior can depend on condition values (hazards are keyed by guard type only), otherwise a staircase cannot be exercised in simulation. Overlaps the display researcher and XC-146. **ENG**.
 21. Test the path, not the piece (CLAUDE.md): a `wlx taskd` session on the simulated card, with a real multi-block plan, through wl-preproc's `decode_stream`/`assemble`, is already specified by SL §9 ("task A with a block plan that recurs (types X, Y, X)"); it exists only if XC-207 is built.

F. Cross-repository.
 22. Format and home of "task programs": wl-xtasks is an empty scaffold (P4d2b §6; XC-150 waits on it); the reference tasks live in this repo's `tasks/`. Whether wl-xtasks tasks follow the same single-`Trial`-per-module rule and where plan declarations sit. **ENG** + wl-xtasks agreement.
 23. Whether `CONDITION`, `TARGET_POSITION` or condition-code allocation in 4096-32767 (wl-xtasks) carries per-trial values in the stream, vs `trials.jsonl` only (S2 §4's rule says content stays in the record; target position is on its "must survive" list). **BOTH**.
 24. Interaction with welfare-critical code: scheduler/levels are not on the welfare list ("No function ... changes", SL §7; PI 2026-09-30: "The list is not widened"); do not add them. If between-trial code could alter reward-related parameters, the boundary where it may not belong in a welfare review (memory: "Welfare list stays as planned").
